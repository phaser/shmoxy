## Description

Fix inspection stream dying permanently on idle: flush SSE headers immediately and treat HttpClient timeout as retryable

## Notes

### Symptom

Live capture shows no traffic and the proxy looks dead, even though the proxy process
started fine and proxies correctly. Reported as "the proxy doesn't start".

### Root cause

Three things compound:

1. Both SSE endpoints (`ProxyControlApi./ipc/inspect/stream` and
   `InspectionController.GetStream`) set the content type and then block waiting for the
   first event. ASP.NET Core withholds response headers until the first write, so an
   **idle** proxy never sends headers and the consumer's request never completes.
2. The frontend's `ApiClient` is registered with no `Timeout`, so the default 100 s
   applies to the `SendAsync(..., ResponseHeadersRead)` stream request.
3. `InspectionDataService.ConsumeStreamAsync` caught `OperationCanceledException` and
   treated it as an intentional stop — `return`, no retry. `HttpClient`'s timeout surfaces
   as `TaskCanceledException`, which derives from `OperationCanceledException`.

Net effect: open Inspection on an idle proxy, and 100 s later the stream is torn down and
never retried. Traffic sent afterwards never appears until the page is reloaded.

### Fix

- Start **and flush** the response before awaiting the first event, in both endpoints.
  `StartAsync` alone only commits the headers; without the flush they never reach the
  client. (Verified end-to-end: this was missed on the first attempt and the unit test
  initially passed anyway — the test now asserts the flush too.)
- Narrow the catch to `when (ct.IsCancellationRequested)` so only a genuine stop ends the
  loop; a timeout now falls through to the existing exponential-backoff retry.

### Not a regression from #344

The reported suspicion was that #344 (bounded streaming) broke this. It did not — the
proxy starts and proxies correctly on that commit, bodies are byte-identical, and
inspection events pair correctly by correlation id. The faulty catch block dates to #288.

### Verification

- Both new tests fail without the fix and pass with it.
- Full suite: 875 passed, 0 failed, 0 warnings.
- End-to-end: idle stream returned headers in <2 s (was 0 bytes indefinitely), and events
  flowed once traffic was sent.

### Follow-up worth considering (not in this PR)

`HttpClient.Timeout` also applies to reads from a `ResponseHeadersRead` content stream, so
a long-lived SSE stream may still be torn down every 100 s. With this fix it reconnects
instead of dying, but a dedicated streaming `HttpClient` with an infinite timeout would
avoid the churn. Left out deliberately — setting an infinite timeout on the shared
`ApiClient` would affect every other API call.
